# Portfolio case-study editorial

Use for case-study content, project explanations, evidence selection, visual storyboards, and portfolio content reviews. Also use when studying references for these tasks. A copy request does not require a redesign. A visual request does not authorize rewriting project history.

## Start with the actual project

1. Read applicable AGENTS.md and the current task. In Anuj's repository, read `docs/portfolio-rules.md`, `docs/case-study-system.md`, `docs/case-study-editorial-update.md`, and the latest relevant restoration/update brief. Check the active branch and existing changes before editing. Historical branch names in notes are not instructions to switch the current checkout.
2. Inspect the current case, its data, original artifacts, sources, and any author account. A public portfolio sentence is a claim to check, not independent proof of its own accuracy. Distinguish the deployed page from the local checkout when they differ.
   Preserve the author's confirmed product purpose separately from the prototype's current coverage. A limited demonstration can narrow implementation claims without redefining the intended problem or reducing open-ended scenarios to the recorded outcomes. Describe expected benefits as predictions when evidence has not established them.
3. Use [the evidence worksheet](templates/case-study-workbook.md) for substantial rewrites. Keep the working records outside visitor-facing copy. For a small correction, use only the relevant part of the worksheet.
4. Consult the source material relevant to the task using the reading map below. Recheck dated project facts when they affect the edit. Do not browse every reference again for every paragraph.

### Borrow deliberately

Before adapting a substantial reference pattern, record its exact page/section, observable feature, inferred reading mechanism, cost, corresponding problem in Anuj's work, available original material, implementation change and acceptance check. Use [the transfer procedure](references/presentation-and-implementation.md). Resemblance must concern a task, information relationship, decision, constraint or evidence problem; visual similarity alone is insufficient.

Separate what the author says from what the reviewer infers. A well-composed detail does not prove the author's intent, and a portfolio's reported result is not independently verified impact. Never use “every detail is intentional” as a substitute for examining the detail. Record unsuccessful, ambiguous and unnecessary patterns as well as useful ones.

For a requested thorough reference audit, inventory linked cases and track each as reviewed, sampled, inaccessible or out of scope with a reason. Include meaningful states and mobile composition where relevant. Do not report a fetched page, thumbnail, HTTP success or directory listing as a complete review. Accessible content, rendered layout, exercised behavior and verified project outcomes are separate kinds of coverage. Stop at access restrictions and retain the gap rather than reconstructing missing work from praise in another article.

The intended reader is provisionally a recruiter or design reviewer assessing interaction/product work. Do not invent an employer brief, reviewer research, or a universal reading-time rule.

## The standard

A reader should understand the situation, what Anuj investigated, what he concluded, why he chose a direction, and what he actually produced or learned. Make the important connections visible:

**Specific situation → evidence → interpretation → decision and trade-off → artifact or behavior → evaluation or current status.**

This is an editorial test, not a claim that every project followed the same process. A documented dead end, constraint, or untested hypothesis can be part of the story. Avoid filling gaps with a plausible retrospective account.

### Evidence and authorship

- Maintain a small claim record: proposed claim, source location, what the source establishes, limits, and publishable wording. Give quantitative, historical, research, ownership, and impact claims particular attention.
- Distinguish original records, the author's account, an inspected artifact, a report's interpretation, and an editorial inference. A screenshot establishes visible design; it does not establish why it was chosen, how it was tested, or what users did.
- Use the past tense for actions supported by a record or confirmed author account. Describe visible behavior in the present. Mark a new design or evaluation as proposed. If the author's historical rationale is missing, describe the current design and ask one focused question when needed.
- Credit the actual work: investigation, synthesis, concept selection, interaction design, implementation, fabrication, testing, and documentation can have different owners. Name collaborators and relevant template, asset, code, or AI assistance without replacing the contribution statement with a tool list.
- A collaborator's site can supply leads and a different account. It cannot automatically grant Anuj that person's research, decisions, or results. Reconcile material discrepancies before changing attribution.
- Prefer the user's confirmed contribution account over ownership inferred from a tool-account name or an exported handoff's account owner. Once clarified, record and reuse it; do not repeatedly reopen the same attribution question. A personal account can use “I” for confirmed work and briefly acknowledge a group without inventing a precise division of responsibilities or labelling group work as solo.
- Preserve neutral public framing where appropriate. Do not turn a concept or learning project into commissioned or deployed work by removing its status.
- Never fabricate research, quotations, participants, personas presented as real people, rejected alternatives, revisions, constraints, dates, test results, or commercial impact.
- Do not create fake sticky-note walls, surveys, interview photos, testimonials, or historical sketches as evidence. A newly made explanatory diagram is allowed if clearly distinguished from an original project artifact in the source record and, when material, the normal story text.
- Do not import another portfolio's numbers, methods, voice, or level of seniority. References guide communication, not Anuj's biography.

### Claim strength

| What exists | What may be said | What still needs evidence |
| --- | --- | --- |
| Visible screen | What information and controls are shown | Historical intent, usability, user preference |
| Functioning browser prototype | Exercised states and inputs in that environment | Production integration, hardware reliability, real-world effectiveness |
| Survey | Answers from the documented sample | Population prevalence, adoption, causal effects |
| Informal feedback | Who tried what and what was reported | Structured usability success or comparative improvement |
| Heuristic review | Expert-identified concerns | Observed user failures or proven fixes |
| Synthetic scenarios | Model behavior under stated assumptions | Real-world predictive accuracy or user outcomes |
| Completed artifact | What was produced and its fidelity | Benefits to users or business |
| Proposed KPI | Target and intended measurement | Achieved result |

For numbers, preserve sample, denominator, missing responses, overlap, time window, measurement method, and attribution as relevant. Prefer counts to impressive percentages for tiny samples. Keep measured, projected, reported, and proposed results distinguishable. A successful build proves compilation, not hardware operation or impact. A before/after screen comparison needs real versions; an improvement claim also needs comparable evaluation.

## Shape the story

Keep Anuj's existing overview and five stages. They are the navigation structure; the content inside them must be project-specific. Preserve current routes and selected projects unless the user requests a selection change.

| Part | Reader's question | Useful material |
| --- | --- | --- |
| Opening and overview | What is this, for whom, what did Anuj do, and what exists? | Genuine product visual, concise introduction, brief, specific problem, confirmed duration, contribution and status |
| Research | What uncertainty was investigated and how? | Actual method, relevant sample/context, selected source material and its purpose |
| Insights | What changed the understanding of the problem? | Specific finding, interpretation, implication, counterexample or limit |
| Concept | Why this direction? | Real alternatives if available, selection criterion, constraint and trade-off |
| Design | How does the choice work? | Legible interface, physical interaction, flow, states or implementation detail tied to the decision |
| Outcome | What happened and what remains open? | Produced artifact, evaluated finding if any, honest status, concrete learning and next check |

- Show what exists early on the case page, then let readers inspect the reasoning. This does not permit project media in the portfolio homepage hero.
- Support scanning through descriptive headings, meaningful section openings, legible artifacts, and working stage links. Keep essential problem, contribution, status, and conclusions visible. Optional disclosure can hold lengthy evidence or extra explorations.
- Preserve the established moderate narrative length; current guidance suggests roughly 540–600 words for main cases, scaled to evidence. Use this as an editing reference, not a quota or reason to delete necessary reasoning. Do not create a deep-dive route merely to imitate a reference.
- Select the decisions that distinguish this project. Usually a few well-supported decisions carry more weight than a complete inventory of activities. Do not invent a minimum number of decisions or alternatives.
- Research needs a question and relevant evidence. Do not repeat the problem statement or explain textbook method definitions. An insight needs an implication. Design needs actual behavior or form, rather than another summary of the concept.
- Explain alternatives only if genuinely explored. If only one version survives, state the existing choice and constraint; request earlier work where useful. Do not redraw rejected concepts and imply they existed during the project.
- Keep honest limitations concentrated where they affect understanding, especially Outcome. Avoid a disclaimer after every paragraph. Keep a qualification beside a metric or status claim when separating it would mislead.
- Open with the person's actual task and the object being designed. Do not make source classification, evidence ethics or the assistant's editing process the main subject unless that is the project. Keep the source register in working documents; make the public story explain a complaint, a dose, a visit or another concrete situation. A compact concept/status statement and a relevant limitation are usually enough. Repeated statements about what is not proven can obscure the work as much as unsupported praise.
- Check the rendered artifact against the final code and state, including later overrides, renamed sample content and version changes. An early data declaration or older case paragraph may be stale even when it is in the same file. A detailed walkthrough must name the dish, control, record or state that actually appears.
- A reflection should say what was misunderstood, what changed, or what would be done differently and why. Generic lessons about empathy, collaboration, or iteration add little without a concrete incident.

## Write in Anuj's voice

Use personal, direct language with accurate ownership. Use “I” for individual work and “we” only where it describes the team. Preserve useful original phrasing and specific detail rather than flattening every case into one assistant voice.

For each paragraph ask:

1. What new fact, interpretation, decision, behavior, or result does this add?
2. Could this paragraph describe almost any design project if the name changed? If so, ground it in a specific task or remove it.
3. Does it explain the connection, or merely place a research claim next to a design claim?
4. Is its certainty supported? Did polishing introduce stronger causality, authorship, scope, or implementation status?
5. Does the artifact show the same thing the text says?

Replace unsupported adjectives with actions and objects. Watch for “seamless,” “intuitive,” “innovative,” “impactful,” “empowering,” “user-centric,” “holistic,” and “transformative.” These are review signals, not an automatic word ban when precise source material requires them. Avoid poetic slogans, invented terminology, methodological name-dropping, repeated “not X, but Y” claims, and canned conclusions.

Example of an editorial rewrite grounded only in the existing Meditimer screens:

- Weak: “An intuitive ecosystem empowers caregivers with seamless medication management.”
- Specific: “The caregiver view shows daily progress and individual dose records, with a call action for following up.”
- The rewrite describes the interface. It does not establish improved adherence, synchronized accounts, or a historical research finding.

Do not convert intended effects into achieved effects. “I grouped the readings to keep their positions stable” needs a supported author account; “The readings keep their positions as values change” needs an exercised prototype; “Riders found readings faster” needs an appropriate evaluation.

## Make the visuals explain

Before choosing a layout, specify the claim the visual should help the reader assess. Use a short visual plan: section, reader question, source artifact, what to inspect, composition, interaction/fallback, and evidence limit.

| Purpose | Suitable material | What the reader must be able to see |
| --- | --- | --- |
| Context | Relevant field photo, task or system view | Where the difficulty occurs and who encounters it |
| Evidence | Actual research extract or scoped aggregate chart | The observation or result supporting the interpretation |
| Decision | Real alternatives or comparable versions | The consequential difference and the stated selection reason |
| Interaction | State sequence, controlled demo, short recording | Starting state, action, feedback, next state, relevant recovery |
| Physical design | Real model photos or operation footage | Scale, handling, controls, assembly or refill, and actual fidelity |
| Outcome | Tested version and scoped result, or delivered artifact | What exists, what was evaluated, and what remains proposed |

- Prefer original material. Show a whole screen to establish context, then a readable detail if the decision needs it. Never shrink six screens until none can be inspected.
- For comparisons, preserve equivalent scale, state, and context. Do not label a cosmetic reconstruction a measured before/after improvement.
- Explain diagrams in normal prose and give them a defined purpose. Do not put a generic Double Diamond, persona, journey map, or system diagram in every case.
- Use composition, grouping, scale, spacing, typography, image sequence, and interaction for hierarchy. Colour and motion need a purpose; retain the existing visual system.
- For Anuj's site, do not add marginal notes, image captions, overlaid annotations, footnotes, subscripts, superscripts, stage numbers, decorative arrows, dots, or em dashes. The approved contact arrow is a specific exception. Retain original research artifacts intact, including their original labels. Put necessary explanation in ordinary case paragraphs and provenance in source records/credits. Keep useful alt text and accessible control names.
- Preserve DM Sans, current palette, footer, text-only homepage hero, and image/title-only project cards. Reference patterns do not supersede these rules. The no-work-in-homepage-hero rule does not prohibit the existing case-page opening visual.
- Preserve the restored Meditimer layout and fixed raster device mockups. Never wrap its screen PNGs in responsive CSS device borders or distort/crop their source proportions.
- Make optional demos supplementary to an understandable static story. Test keyboard, touch, reduced motion, narrow layouts, full-size viewing and no-JavaScript access when changing those features. Do not hide the conclusion behind hover or autoplay.

## Deliver and check

For a substantial refinement deliver the requested artifact, together with only the working records needed to review it:

1. A brief diagnosis with exact locations and priority: unsupported claims/ownership first, reasoning and missing evidence next, presentation polish after that.
2. Refined copy or an applied patch, with source-backed facts preserved.
3. A visual plan tied to the selected decisions and real assets. Name missing assets precisely instead of filling them with stock images or generated evidence.
4. A short evidence/questions list. Ask only for facts that materially change the story; continue independent edits.
5. A report of what was checked and what remains uncertain. Do not claim user testing, verification of project outcomes, or deployment from an editorial review.

Before finishing, perform [the acceptance review](references/acceptance-review.md). If content is implemented, inspect the actual rendering at desktop and phone widths and run repository-required checks appropriate to the change. A documentation-only skill change does not need the app build. Do not merge, publish, push, save memories, start unrelated services, or redesign unrelated areas just because this skill was invoked; use the current task's authorization.
