There is a useful foundation here: interests across people, systems, interfaces, and physical objects, with working implementations to inspect. The earlier portfolio made it difficult to assess that foundation. Empty media blocks, a long opening, generic philosophy, and unsupported research claims weakened both craft and credibility.

This branch improves the first impression and the accuracy of project descriptions. It is not yet a complete, competitive case-study portfolio. The next gains require original artifacts, specific decisions, clear individual contributions, and documented iteration. More animation alone cannot supply those things.

## What strong portfolios communicate

There is no universal visual style that guarantees quality. Reviewers need answers to these questions:

| Question | Useful evidence | Current priority |
| --- | --- | --- |
| What work could I give this person? | Relevant projects and a concrete introduction | Interaction, information, and physical/digital work now appear together. |
| Can they resolve an interface? | Readable screens, typography, states, responsive behaviour | Two genuine project images replace homepage placeholders; original screen sets are still needed. |
| Can they make a defensible decision? | A constraint, alternatives, choice, and consequence | Add two or three specific decisions per main case. |
| Can they learn from evidence? | Actual observation or testing, a resulting change, and limitations | Retrieve original research; remove unsupported precision. |
| What did they personally do? | Ownership, collaborators, third-party assets, and assistance | Separate group Meditimer work, the independent app, and generated implementation. |
| Can they execute and collaborate? | Working demos, connected states, documentation | Source and demos help, but do not prove hardware or user outcomes. |
| What happened after the design? | An observed result, tested limitation, or unfinished status | No invented impact percentages or participant quotes. |

The desired takeaway is: “They can investigate an unfamiliar problem, choose a direction, make its behaviour tangible, and explain what they learned.” A tool list cannot demonstrate that.

## Why this visual change helps

The opening places an introduction beside a project in unequal columns. The circular instrument and panoramic web capture receive different surfaces and proportions. Colour, an italic accent, and varied alignment add character while navigation remains predictable.

Visitors choose the featured project; movement follows that choice. The global entrance fade was removed so server-rendered content is visible immediately. Mobile stacks the content in reading order, and reduced-motion preferences disable the new movement.

The question-led headline is a design proposal, not a personal quotation. This branch is the concrete version to review. More expressive interactions can come from inspectable states, original sketches, annotated alternatives, and physical-prototype footage once those artifacts are available.

## Project priorities

### Himalayan 450

**Potential:** constrained interface hierarchy, state design, and prototyping.

**Available:** a genuine circular interface export, a deployed browser prototype, and documentation describing ignition, speed, gears, indicators, and modes. The README credits Copilot assistance. This is an independent educational concept, unaffiliated with Royal Enfield.

**Next:** define the intended situation; compare the original design with one meaningful alternative; explain two hierarchy decisions; capture changing states; distinguish personal design decisions from generated implementation. Retrieve actual research before quoting participants, percentages, or riding observations. Browser simulation does not establish sunlight readability, safe operation, or reduced glance time.

**Useful sequence:** context → competing signals → alternatives → chosen hierarchy → state demonstration → tested findings and limits.

### India in Orbit

**Potential:** information architecture, storytelling, visual composition, and implementation of a complex subject.

**Available:** the linked repository, live website, actual screen capture, mission and orbit sections, propagation code, and visible methodology and credits. The site credits Anuj Rai for design/development and Dr. Anupam Rana for guidance. Preserve these alongside asset and assistance attribution.

**Next:** define an audience and a useful question; explain why everyday applications precede orbital detail; show one before/after interaction; audit data sources, freshness, fallback behaviour, and scientific claims. Review mobile performance and alternatives to 3D. A working renderer alone does not establish comprehension or scientific accuracy.

**Useful sequence:** audience question → fragmented information → content structure → interaction choice → working example → comprehension and performance findings.

### Independent medicine app

**Potential:** a complete digital flow with clear ownership; the user described developing it independently.

**Unavailable here:** its repository/prototype, actual states, and original documentation. Do not substitute the physical medicine concept or invent screens.

**Next:** inspect the app; show one complete task with empty, error, and recovery states; explain why reminder behaviour fits its context; distinguish implemented features from concepts. Include feedback and resulting changes if documented.

### Physical Meditimer

**Potential:** problem framing across an object and a routine.

**User-reported ownership:** Anuj contributed concept framing and rationale; teammates contributed mockups and documentation. Its route remains a brief, separate from the independent app.

**Next:** retrieve group material and research; attribute artifacts; explain one physical-interaction tradeoff; show what changed. The old site's five-family claim, specific routines, paper testing, and participant quote were unverified and have been removed.

### Intelligent Waste Disposal Systems

**Potential:** embodied interaction, expressive feedback, state transitions, and making. The user described building the physical prototype.

**Available:** firmware/documentation for sensors, OLED eyes, audio, and a servo lid. Code describes implementation; it does not demonstrate actual hardware operation.

**Next:** show the real object responding, a state diagram tied to observed behaviour, one iteration, and personal contribution. Evaluate whether feedback is understandable; expressive eyes alone do not prove behaviour change. Promote it from Lab when the evidence supports a focused story.

### Toki

**Potential:** connected-product interaction and recovery behaviour.

**Available:** the current AnujR17 repository is a connection-first BLE lab with a minimal app/web probe. Its documentation says a handshake does not establish final combined firmware. It differs from the fuller Toki experience discussed previously.

**Next:** identify the current hardware/app revision; record successful connection, failure, reconnection, and recovery; then document the integrated experience. Keep it ongoing until demonstrated. Do not present task lists, motors, e-paper, or audio as verified integrated features from this repository.
